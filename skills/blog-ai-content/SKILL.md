# Blog AI 内容规范

把资料转换为博客可直接审核的 Markdown。四个学科窗口共用本 Skill；学科、角色名、头像和输出目录由当前窗口或主管提示词提供，不要臆造账号，也不要把“AI 学科助教”等技术标签写入正文。

## 交付边界

- 原始输入可以是 PDF、DOCX、网页、图片 OCR、纯文本或用户对话；先读取并核对来源，再只交付 Markdown 正文。不要要求博客上传原始文件。
- 文章正文遵循仓库现有 Markdown 渲染链路（优先检查 `lib/markdown.ts` 与 `components/ui/MarkdownContent.tsx`），不要发明新的语法、front matter 或自定义 HTML 组件。
- 普通文章后端把 `title`、`content`、`type`、`subject`、`tags`、封面/视频/题目等字段分开保存；`content` 只放 Markdown 正文，不在正文前后包 YAML front matter。`is_published`、作者归属和版本由博客审核链控制。
- 文章的作者、头像、角色名、简介、学科和擅长方向属于 `ai_profiles`/审核元数据；正文只写正常内容。不要修改人工文章、人工作者字段或其他学科资料。
- 需要文件时遵守当前窗口给出的目录和命名规则；没有给出目录时先输出内容，不擅自写入项目或生产数据库。

## 工作流

1. **辨识任务**：判断是普通文章、知识点笔记、讲义、合集章节还是已有文章修订；记录来源范围、目标读者和压缩程度。
2. **提取与核对**：保留定义、机制、条件、公式、例外、结论和必要的例子。长讲义应按章节拆成多篇独立 Markdown；不要把 18 章压进一篇超长文章。章节顺序、标题和合集归属作为元数据或交付清单说明。
3. **生成正文**：先写清晰的 H1 标题，再用连续的 H2/H3 组织内容；每个标题下有实质正文。按“概念 → 机制/推导 → 例子 → 易错点/小结”组织，但学科需要时可调整。
4. **处理媒体**：只有用户明确要求时才插入图片；Bilibili/YouTube 引用使用博客已有视频语法或组件。需要动态解释图像时，先说明数据和交互意图，不把静态截图冒充动效。
5. **附加快测建议**：讲义可以另附知识点快测草案或生成要求，但题目、选项、答案和解析不写进 Markdown 正文。题目应覆盖本章重点，标出知识点、难度和来源标题；最终由博客工作流单独生成、审核、发布和判分。
6. **静默自检后交付**：生成完成后先自行修正问题，再交付最终版本。不要展示内部修改历史；只在发现无法安全修复的事实或来源缺口时列出阻塞项。

## Markdown 自检清单

提交前逐项确认：

- H1 只有一个且与文章标题一致；标题层级连续，不跳过 H2 直接使用 H4。
- 段落之间留出清晰空行；列表、引用、表格和代码围栏成对闭合。
- 行内数学使用 `$...$`，独立公式使用 `$$...$$`；不要把 LaTeX 反斜杠写成双重转义文本。
- 代码块带正确语言标识；代码、公式和表格内部不被普通段落重排破坏。
- 链接可识别，图片/视频语法符合仓库现有渲染器；没有无意义的裸 HTML、内联样式或脚本。
- 不重复标题，不堆叠空行，不用“本文将……”作为大量空泛开场；中文标点、术语和变量命名一致。
- 精简讲义时逐章检查关键知识点、公式、假设、反例和结论没有被压掉；不确定内容标注“待核对”，不编造页码或来源。
- 正文不泄露私有答案、审核操作、账号 token、内部路径或自检日志。

## 输出格式

默认按以下顺序返回：

1. `标题`（与 Markdown H1 一致）；
2. `Markdown` 代码块（只放可写入博客正文的内容，不混入答案或审核说明）；
3. `章节/合集清单`（仅当任务涉及讲义拆章或合集）；
4. `知识点快测建议`（仅当用户要求，列题型、覆盖知识点和难度，不泄露最终答案到正文）；
5. `待核对项`（没有则写“无”）。

若用户要求直接写文件，先确认目标路径在当前项目范围内，再使用现有文章格式写入；写入后重新读取并做一次 Markdown 自检。不要执行生产迁移、账号 provisioning、发布或部署。

## 与博客功能的对应关系

- AI 内容工作台：生成/更新自己的 Markdown 提案，等待博客端自检和人工审核。
- 审核工作台：正文、批注、版本和发布由用户决定；Skill 不代替人工批准。
- 合集：章节可以今天、明天分批加入同一合集；不要假设合集一次性上传完成。
- 笔记阅读助手：只回答当前笔记范围；快测必须在博客端审核发布后才可调用。
- 角色扮演开关：如果用户关闭角色显示，正文仍保持正常内容，不强行插入角色称谓。
